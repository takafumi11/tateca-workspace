# Requirements Document — 認証ユーザー管理

## Introduction

Tateca は旅行・食事・イベントなど日常の割り勘シーンにおける共有費用を管理するアプリケーションである。
認証ユーザー管理は、Firebase 認証アカウントに対応するシステム内のユーザーレコードの作成・取得・削除、およびアプリレビュー設定の更新を扱う。

認証ユーザーはシステムへの初回ログイン時に作成される。情報取得のたびにログイン記録（累計ログイン回数・最終ログイン日時）が更新される。削除時はアプリ内ユーザーとの紐付けを解除してからレコードを削除する。

## Scope

- 認証ユーザーレコードの新規作成
- 認証ユーザー情報の取得（ログイン記録更新を含む）
- 認証ユーザーレコードの削除（アプリ内ユーザーとの紐付け解除を含む）
- アプリレビューステータスの更新

### Out of Scope

- メールアドレスの形式検証（空白チェックと長さチェックのみ）
- 表示名の設定（作成時は空文字で初期化される。グループ作成時にメンバー名として設定される）
- Firebase アカウント自体の作成・削除（Firebase 側で完了済みである前提）
- 作成・削除完了後の通知
- メールアドレスの前後空白除去（トリムせずそのまま保存される）
- ログイン記録を更新しない参照専用の取得
- ログイン履歴の保持（最新のログイン情報のみ保持）
- 要求者と取得・削除対象の同一性検証（認証済みであれば任意の UID を指定可能）
- アプリ内ユーザーレコード自体の削除（紐付け解除のみ）
- アプリレビューステータスの遷移制約（任意のステータスへの変更が可能）
- 同値更新の最適化（同じステータスへの更新でもレビューダイアログ最終表示日時は更新される）

## Common Preconditions

すべての要件は以下を暗黙の前提とする。

- 要求者は認証済みである

## Domain Definitions

- **認証ユーザー:** Firebase 認証アカウントに対応するシステム内のユーザーレコード。一意の識別子（UID）で特定される
- **UID:** 認証ユーザーを一意に識別する文字列。要求者の認証情報から自動的に取得される、または URL パスで指定される
- **メールアドレス:** 認証ユーザーに紐付くメールアドレス。システム全体で一意である必要がある
- **アプリ内ユーザー:** グループに所属するメンバーレコード。認証ユーザーと紐付けられている場合がある
- **紐付け解除:** アプリ内ユーザーから認証ユーザーへの参照を削除すること。アプリ内ユーザーレコード自体は保持される
- **アプリレビューステータス:** アプリストアレビュー依頼の状態を示す値。「保留（PENDING）」「完了（COMPLETED）」「永久拒否（PERMANENTLY_DECLINED）」のいずれか
- **レビューダイアログ最終表示日時:** アプリレビュー依頼ダイアログが最後に表示された日時

## Requirements

### Requirement 1: 認証ユーザーの作成（正常系）

**User Story:** 新規ユーザーとして、初回ログイン時にアカウントをシステムに登録したい。アプリの全機能を利用するため。

#### Acceptance Criteria

1. GIVEN 要求されたメールアドレスがシステムに未登録である WHEN メールアドレスを指定して認証ユーザー作成を要求する THEN システム SHALL 認証ユーザーレコードを作成し、作成された情報を返す
2. GIVEN 認証ユーザーが作成された WHEN 作成時の初期値として THEN システム SHALL ログイン回数を 1 に設定し、アプリレビューステータスを「保留」に設定する
3. GIVEN 認証ユーザーが作成された WHEN 最終ログイン日時として THEN システム SHALL 作成日時を最終ログイン日時に設定する

---

### Requirement 2: 入力バリデーション（作成）

**User Story:** システム管理者として、不正な入力によるアカウント作成を防ぎたい。

#### Acceptance Criteria

1. GIVEN リクエスト入力が不正である WHEN 認証ユーザー作成を要求する THEN システム SHALL 入力不備として拒否する

> フィールドレベルの詳細（必須項目、文字数制限、形式制約など）は API Contract (OpenAPI) で定義する。

---

### Requirement 3: メールアドレスの一意性

**User Story:** システム管理者として、同一メールアドレスによるアカウントの重複登録を防ぎたい。データの整合性を保つため。

#### Acceptance Criteria

1. GIVEN 指定されたメールアドレスが既に別の認証ユーザーに登録されている WHEN 認証ユーザー作成を要求する THEN システム SHALL 重複として拒否する

---

### Requirement 4: 認証ユーザー情報の取得とログイン記録更新（正常系）

**User Story:** 認証済みユーザーとして、自分のアカウント情報を取得したい。アプリ起動時にプロフィール情報を表示し、ログイン記録を残すため。

#### Acceptance Criteria

1. GIVEN 指定された UID に対応する認証ユーザーが存在する WHEN 認証ユーザー情報の取得を要求する THEN システム SHALL 認証ユーザーの情報を返す
2. GIVEN 認証ユーザー情報の取得が成功した WHEN 取得時の処理として THEN システム SHALL ログイン回数を 1 加算し、最終ログイン日時を現在日時に更新する
3. GIVEN 認証ユーザー情報の取得が複数回行われた WHEN 各取得のたびに THEN システム SHALL ログイン回数を累積的に加算する

---

### Requirement 5: 入力バリデーション（取得・削除）

**User Story:** システム管理者として、不正な入力による情報取得や削除を防ぎたい。

#### Acceptance Criteria

1. GIVEN リクエスト入力が不正である WHEN 認証ユーザー情報の取得または削除を要求する THEN システム SHALL 入力不備として拒否する

> フィールドレベルの詳細（必須項目、文字数制限など）は API Contract (OpenAPI) で定義する。

---

### Requirement 6: 認証ユーザーの削除（正常系）

**User Story:** ユーザーとして、アカウントを削除したい。サービスの利用を終了するため。

#### Acceptance Criteria

1. GIVEN 指定された UID に対応する認証ユーザーが存在する WHEN 認証ユーザー削除を要求する THEN システム SHALL 認証ユーザーレコードを削除する
2. GIVEN 認証ユーザーに紐付くアプリ内ユーザーが存在する WHEN 認証ユーザー削除を要求する THEN システム SHALL 削除前にすべての紐付くアプリ内ユーザーから認証アカウントの参照を解除する
3. GIVEN 認証ユーザー削除が完了した WHEN 紐付け解除されたアプリ内ユーザーを確認する THEN システム SHALL アプリ内ユーザーレコードは削除されず保持されていること

---

### Requirement 7: リソース不存在

**User Story:** 要求者として、存在しない認証ユーザーに対する操作には適切なエラーを受け取りたい。

#### Acceptance Criteria

1. GIVEN 認証済みユーザー WHEN 存在しない UID で認証ユーザー情報の取得を要求する THEN システム SHALL リソース不在として拒否する
2. GIVEN 認証済みユーザー WHEN 存在しない UID で認証ユーザー削除を要求する THEN システム SHALL リソース不在として拒否する
3. GIVEN 認証済みだが対応する認証ユーザーレコードが存在しない WHEN アプリレビュー設定の更新を要求する THEN システム SHALL リソース不在として拒否する

---

### Requirement 8: アプリレビュー設定の更新（正常系）

**User Story:** ユーザーとして、アプリレビューの設定を更新したい。レビュー依頼ダイアログの表示を適切に制御するため。

#### Acceptance Criteria

1. GIVEN 要求者に対応する認証ユーザーが存在する WHEN 有効なアプリレビューステータスで更新を要求する THEN システム SHALL アプリレビューステータスを指定された値に更新する
2. GIVEN アプリレビュー設定の更新が成功した WHEN 更新時の処理として THEN システム SHALL レビューダイアログ最終表示日時を現在日時に更新する
3. GIVEN 任意の現在のステータスである WHEN 3 種類のいずれかのステータスで更新を要求する THEN システム SHALL ステータスの変更を受け入れる

---

### Requirement 9: 入力バリデーション（アプリレビュー設定更新）

**User Story:** システム管理者として、不正な入力によるレビュー設定の更新を防ぎたい。

#### Acceptance Criteria

1. GIVEN リクエスト入力が不正である WHEN アプリレビュー設定の更新を要求する THEN システム SHALL 入力不備として拒否する

> フィールドレベルの詳細（必須項目、許容値など）は API Contract (OpenAPI) で定義する。
