# Review Criteria

Record the review in `docs/specs/{feature}/reviews/` in the current repo. Use the common format in `platform/docs/sdd-process.md` and `platform/docs/review-record-template.md`.

After recording findings, run **Review → Triage → Fix → Re-review** from `review-record-template.md` until the step can close.

A Step 2 review covers both halves at once. Run every perspective listed below in the same review record.

| Review | Check |
|--------|-------|
| Architect | Flow correctness, repo ownership clarity, state model, integration and recovery soundness, explicit recovery-path routing, irreversible data-model decisions, amount-source / finalization rules where mode or idempotency matters, comparable granularity across multiple behavior paths, and consistency between the canonical flows and the contract surface |
| Tech Lead | Feasibility, alignment with `requirements.md`, frontend handoff clarity, OpenAPI surface clarity (paths, schemas, status / error codes, grouped examples), explicit Step 1 to Step 2 technical handoff (per-field validation in OpenAPI; persisted-value rules and side effects in `design.md`), test ownership, operability, and verification entrypoints that reflect the real verification path including manual checks where applicable |
| Test Author | `Canonical Testable Flows` show DB and KVS side effects per node and name dropped legacy gates as explicit non-gates, every Mermaid `flowchart TD` is preceded by the convention banner and splits intermediate side-effect nodes from terminal response nodes (HTTP status codes only on terminals; one terminal per distinct response variant; persistence pre-state branched explicitly; conditional best-effort writes stated in node text), `Assertion Rules For Test Authors` covers the rules tests must enforce — including external-to-internal error conversion (external code, internal causes, and that the response body never carries the internal cause), post-success rollback, versioned-row trajectory, and idempotent-confirmation behavior — `QA E2E Matrix` and `QA Contract E2E Matrix` cover every QA-owned scenario with response, DB, and KVS assertions, and `Developer Verification Policy` clearly carves out branches QA cannot reproduce. Scenario IDs follow the contiguous-namespace convention: QA owns `S01..Sn`, dev owns `Sn+1..Sm`, the Dev-Only Verification table has a `Scenario ID` column, coverage rules carry `—`, no gaps, no `S##a`/`S##b` sub-IDs, and the carve-out paragraph names the QA and dev ranges explicitly |
| Consumer Engineer | Request usability, required vs optional clarity, error handling usability via the per-response `Internal code | Message` table plus grouped examples per HTTP status, async or polling clarity for backend callers, and example usability for callers (Business Rules summary stays caller-facing and short) |
| QA Question Prevention | `Canonical Testable Flows` plus `Assertion Rules For Test Authors` already answer the recurring questions in the `QA Question Prevention Heuristic` table from [Design Guide](design-guide.md): post-success rollback semantics, idempotent-response handling, multi-cause-to-one-code conversion, `version` trajectory across steps, removed legacy gates, vendor body code remap, best-effort side-effect outcome, async / accepted semantics, `external_ref_key` rules, and daily-limit semantics |
| Sanity | Contradictions between paths, schemas, examples, and `design.md` sections; missing `$ref` targets; inconsistent requiredness, status, error semantics, or caller-visible behavior; design narrative leaking into OpenAPI or contract detail leaking into `design.md`; asymmetric detail between request and recovery / batch paths; ungrounded assumptions; `External Outcome Mapping Snapshot` and `Assertion Rules For Test Authors` disagreeing on the conversion rule for the same external code |
